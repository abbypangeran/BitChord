# BitChord v1.9.29 — PCM sample-accuracy and digital null test

**Date:** 2 November 2026 · **Publication branch:** `bitperfect-validation` (based on the `macos` publication candidate) · **Production code changed:** none

## Outcome

**`EXACT`** at the Java Sound `SourceDataLine.write()` boundary, for every lossless-expected path tested:
65 captures, 14,818,810 samples, 0 mismatches, with app volume at 100 % and all optional DSP off.

> [!IMPORTANT]
> This proves only that the bytes BitChord hands to Java Sound are the FLAC's exact PCM samples. It does **not** establish bit-perfect transmission through Java Sound's CoreAudio backend, macOS CoreAudio (mixer, format conversion, volume), the USB driver or the ONIX Alpha XI1. Matching sample rate, matching bit depth or the DAC's display do not prove that either.

## Boundary and path under test

Production signal chain for a single, unblended local track (all in `desktopApp/src/main/kotlin/com/music/bitchord/desktop/`):

1. `DesktopAudioDecoder.open/readSamples` — JavaCPP FFmpeg 7.1.1 FLAC decoder, then `swr_convert` to interleaved `AV_SAMPLE_FMT_FLT` at the source rate (the request `DesktopPlaybackEngine.openTrack` makes).
2. `DesktopDecodeAhead` — read-ahead thread; copies float blocks.
3. Engine stages (`DesktopAudioEngine.kt` `step/blend/play`): `DesktopSpatialAudio` (off), `DesktopEqualizer` (off + flat), crossfade/Automix blend (none), `DesktopSilenceSkipper` (off), `DesktopAudioSpeed` (1.0), `limitOutput` (not engaged: `needsOutputLimit` false). Each disabled stage returns its input untouched. `DesktopRateConverter` is used only when decoder rate ≠ sink rate; hardware-rate matching keeps them equal.
4. `DesktopAudioSink.write` → `convert` → `packPcm(samples, count, format, gain, out)` → **`SourceDataLine.write(bytes, 0, count * bytesPerSample)`** (`DesktopAudioSink.kt` line 165). This is the capture point.

Capture method: the test (`DesktopBitPerfectValidationTest`) puts a recording `SourceDataLine` proxy into the sink's private `line` field by reflection, so the unmodified `write → convert → packPcm → line.write` code runs and no device is opened. Stages 1–3 are the production classes, called in the engine's order; the `DesktopPlaybackEngine` thread itself is not run (it needs a resolved `Song`/stream and a real device), so its orchestration is reproduced, not executed.

On the test host, Java Sound's query-only default-mixer check rejected float and 32-bit integer lines, so `negotiatePcm` selected signed 24-bit little-endian PCM (`bytesPerSample=3`) at the tested rates. The capture itself used a recording `SourceDataLine` proxy; no audio device was opened. This host capability check is not evidence of DAC output. The original private build's ONIX Alpha XI1 hardware acceptance is described separately in `docs/macos-preview.md` and does not extend to this publication candidate.

## Test material

Generated by `tools/bitperfect/generate.py` (NumPy, fixed seeds), encoded by `flac 1.5.0 -8 --verify`, then decoded independently by `flac -d` **and** Homebrew `ffmpeg 8.0.1`; both matched the reference exactly for all 20 files before BitChord was tested. Every file is stereo with different left/right content (catches channel swaps) and 2 s + 37 frames long (not a multiple of any FLAC block size).

| Signal | Content |
|---|---|
| `silence_impulse` | digital silence with single-sample impulses: ±1 LSB, +full-scale, −full-scale, one per channel |
| `full_scale` | alternating +8388607/−8388608 (and 16-bit equivalents), then near-boundary values |
| `lsb` | −4…+4 LSB staircase (L), ±1 LSB square (R) |
| `random` | deterministic uniform PCM over the full integer range |
| `sines` | 100 Hz + 1 kHz + 10 kHz (L), 440 Hz + 3 kHz + 15 kHz (R), −1 dBFS |

Formats: 24-bit at 44.1, 48 and 96 kHz; 16-bit at 44.1 kHz. Frames: 88,237 (44.1 kHz), 96,037 (48 kHz), 192,037 (96 kHz). SHA-256 of every FLAC and reference, and the FLAC STREAMINFO MD5, are in `build/bitperfect/fixtures/manifest.json`.

### Differences between output formats

- **S24, S32, float:** all lossless for 16- and 24-bit sources. Float is exact because 24-bit integers fit in a float's 24-bit significand; FFmpeg's S32/S16→FLT scaling is a power of two; `packPcm` multiplies by 2^(n−1) in `double` and `toLong()` gets an integer with nothing to truncate. +full-scale (`8388607/2^23 < 1`) does not clip, and −1.0 maps to `−limit` exactly.
- **24-bit source → S16** (only when the user picks 16-bit output precision): `packPcm` **truncates toward zero** (`toLong()`), with no rounding or dither. Verified against all 15 files: matches `trunc(x/256)` exactly, not `floor` or round-to-nearest. Max error 255 (24-bit LSBs), i.e. under one 16-bit LSB; RMS ≈ 147 on wideband signals. Sub-256-LSB detail such as the ±1 LSB impulses disappears. Precision loss is inherent here, but truncation toward zero adds a small sign-dependent bias and correlated distortion that rounding plus TPDF dither would avoid. Selecting 24-bit output avoids this specific 16-bit truncation behavior; it does not establish DAC-wire accuracy.
- **App volume below 100 %:** `DesktopAudioSink.gain` scales every sample digitally in `packPcm`, so playback is not bit-exact at any volume other than 1.0 (shown at 0.5: values halved and truncated).

## Defects

None on the tested lossless path. One low-severity observation, outside the validated configuration:

- `packPcm` requantises to 16-bit by truncation without dither. Minimal fix, if you want it (not applied): round to nearest, optionally with TPDF dither, only when `bytesPerSample * 8` is less than the source depth. Leave the S24/S32/float paths alone; they are already exact.

## Conditions under which output is *not* exact at this boundary

App volume ≠ 100 %; equaliser, spatial audio, playback speed, skip-silence on; during crossfade or Automix blends (gain ramps plus the output limiter); any time the line opens at a rate other than the source's (`DesktopRateConverter`, e.g. hardware-rate matching off or unsupported); 16-bit output precision with 24-bit sources. Seeks are trimmed sample-accurately but were not part of this null test.

## Reproduce

```sh
git switch bitperfect-validation
tools/bitperfect/run.sh            # generate + capture + null test; exit 0 only if no unexpected difference
# artefacts: build/bitperfect/{fixtures/manifest.json,captures/capture.json,results.json}
```

Requirements: `flac`/`metaflac`, `ffmpeg`, `python3` + NumPy, JDK 21 (`JAVA_HOME_21` or the Homebrew path in `docs/macos-preview.md`). No DAC, no Lossless Bridge addon, no streaming service and no app install are needed, and no audio device is opened. `XDG_STATE_HOME` is redirected so that the user's `desktop.log` is not touched. Without `BITCHORD_BITPERFECT_DIR` set, the test is a no-op, so the normal `:desktopApp:test` stays self-contained.

Two consecutive runs gave byte-identical artefacts: `results.json` SHA-256 `6b2dd5e2cd799f2f7917c193679b50bf1525bc80597605892338d071d31f6bc3`, `manifest.json` `16bd03b6a7b5702c6b404adca891f28f092a58947493b6c930925e0d291c6f10`.

Regression (JDK 21, `:desktopApp:test :shared:jvmTest :sharedUi:jvmTest`, validation enabled): desktop 373 passed (the baseline's 372 plus this test), shared 122 passed, shared UI 42 passed, 0 failures, 0 skipped.

Negative control: changing one reference sample by 1 LSB made both the Gradle test (exit 1, `unexpected sample differences`) and `compare.py` (exit 1, `NOT_EXACT`, 3 captures) fail.
